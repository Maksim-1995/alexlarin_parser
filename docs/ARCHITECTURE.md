# Фактическая архитектура AlexParser

Документ описывает существующий код. Команды запуска и конфигурация находятся
в [README](../README.md), правила разработки и требования заказчика —
в [.agents/agents.md](../.agents/agents.md), особенно в §§8–11, 14 и 16–18.
Здесь не вводятся дополнительные разрешения на обработку данных или вызовы API.

## 1. Общая архитектура

AlexParser — Python CLI для обработки тренировочных вариантов `alexlarin.net`.
Один последовательный конвейер загружает источники, распознаёт условия,
переносит опубликованные ответы, классифицирует задачи и создаёт Excel,
отдельные рисунки и ZIP для каждого варианта. Базы данных, веб-сервера,
очереди задач и параллельной обработки в основном конвейере нет.

Точки входа — корневой [main.py](../main.py) и пакетный
[__main__.py](../alexlarin_parser/__main__.py). Обе вызывают
[cli.cli()](../alexlarin_parser/cli.py). CLI выбирает один URL, набор номеров
из каталога или манифест для возобновления. Обработкой управляет `run_batch`
из [pipeline.py](../alexlarin_parser/pipeline.py).

Реализация находится в пакете `alexlarin_parser/`. Перенесённые корневые
модули, например `pipeline.py`, `classification.py` и `variant_ocr.py`,
сохраняют совместимость импортов. Новые изменения направляются в модуль
пакета, которому принадлежит функция.

## 3. Поток данных от источника до Excel

```text
CLI → VariantContext → SOURCES → OCR → CLASSIFICATION → EXPORT
                           │       │          │            │
                           │       │          │            └─ Excel + рисунки + ZIP
                           │       │          └─ проверенные категории
                           │       └─ задачи, продолжения и ответы с изображений
                           └─ HTML/PDF/JS/PNG, метаданные и исходные метки

После EXPORT: применение содержательной сверки → итоговый статус
Манифест и отчёты сохраняются по мере выполнения этапов.
```

1. До модельных вызовов проверяются полные справочники. Номера вариантов
   выбираются по реальным `href` архива; одиночный URL и `--resume` задают
   контексты напрямую.
2. `prepare_sources` проверяет HTML/PDF и их принадлежность варианту,
   сохраняет происхождение файлов, извлекает метаданные, опубликованные
   HTML/JS-ответы и доступные изображения ответов. Текстовый слой PDF помогает
   определить метки, страницы и расположение задач.
3. `recognize_variant` читает совместимые кэши страниц либо отправляет
   изображения в OCR. Реальные колонки одной страницы передаются одним запросом.
   Изображения опубликованных ответов прикладываются к последней странице;
   поле `answers` отделено от условий. Проверенные фрагменты собираются по меткам.
4. `pipeline` сопоставляет ответы с задачами. HTML/JS имеют приоритет при
   конфликте с OCR, конфликт становится предупреждением. Отсутствующий ответ
   остаётся пустым, `solution` всегда пустой. Проверенный ручной перенос
   ответов 13–19 предусмотрен только для точного источника прежнего варианта 542.
5. `classify_variant` читает совместимый кэш или классифицирует все задачи
   одного варианта одним запросом. Модель выбирает независимые E/T-коды;
   код переводит их в категории и проверяет полноту результата. Затем, при
   наличии отдельного файла, применяются проверенные ручные категории и условия;
   семантические предупреждения относятся уже к итоговым значениям.
6. `export_variant` работает с копиями задач: извлекает рисунки, оформляет
   таблицы, формулы, подпункты и ответы. Excel и ZIP создаются во временном
   каталоге, проверяются и публикуются с резервной копией и откатом при ошибке
   самой замены файлов.
7. Применяется только содержательная сверка с подходящим fingerprint.
   Предупреждения, пропуски ответов или отсутствие подтверждённой сверки дают
   `NEEDS_REVIEW`. Ошибки этапов фиксируются в отчёте; прежний и текущий
   результаты различаются через `previous_result` и `result_current_attempt`.

Excel имеет ровно два листа. Колонки `Tasks`:

```text
task_num, condition, image_name, solution, answer, exams_id, topics_id
```

Колонки `about`:

```text
class, year, date, topic, exam_id, title, code, source_name, is_public, source_url, description
```

Одна строка `Tasks` — одна основная задача со всеми подпунктами. Ответы
сохраняются текстом. Несколько файлов рисунка перечисляются в `image_name`
настоящими переводами строки. ZIP содержит `tasks.xlsx` и только относящиеся
к нему рисунки на одном уровне; источники и диагностика остаются вне выдачи.
Полный контракт и проверки ZIP закреплены в §8 подробных инструкций.

## 4. AI-провайдеры и конфигурация

| Провайдер | Реальная интеграция |
|---|---|
| Gemini → NVIDIA NIM → Groq → OpenRouter `:free` | Основной CLI через один `DeepSeekClient`, если заданы ключ и модель этапа |
| DeepSeek | Последний, платный резерв того же клиента |
| Прежние интеграции Gemini/NVIDIA | Корневые Gemini-утилиты, legacy-кэш 542 и отдельный профиль `check_deepseek.py --provider nvidia` сохранены |

Порядок цепочки фиксирован; провайдер без модели текущего этапа пропускается.
Читаются `<PREFIX>_API_KEY`, `<PREFIX>_OCR_MODEL` и
`<PREFIX>_CLASSIFICATION_MODEL` для GEMINI/NVIDIA/GROQ/OPENROUTER.
Одного ключа недостаточно; DeepSeek-ключ для успешного бесплатного этапа не нужен.
Первый успешный ответ завершает цепочку. 429/503/тайм-аут включают cooldown
бесплатного провайдера; `Retry-After` учитывается числом или HTTP-датой.

Настройки основного потока определяет `DeepSeekSettings`, шаблон переменных —
[.env.example](../.env.example). Основной CLI читает локальный `.env`;
уже заданные переменные окружения приоритетны, shell-подстановки не выполняются.
Прежние Gemini-инструменты и `check_deepseek.py` читают окружение процесса.
В коде исходная модель DeepSeek — `deepseek-flash`. Только DeepSeek получает
thinking: OCR отключает его, классификация имеет отдельную настройку.

У основного DeepSeek-клиента отключены автоматические HTTP-повторы и редиректы.
Счётчик увеличивается перед фактической отправкой; тайм-ауты и неуспешные
ответы входят в число попыток, включая каждый переход цепочки.
HTTP 401/402/403 отключают отказавшего провайдера; отказ DeepSeek блокирует
дальнейшие платные обращения, но сохраняет бесплатные для следующих вариантов.
В манифесте цепочка обозначается `fallback-chain`, фактический провайдер —
в каждой записи `attempts`. Загрузки источников учитываются отдельно. Расчёт стоимости
по тарифам не реализован: `cost` всегда `None`. Неполный usage отмечается через
`unknown_usage_attempts`; неизвестные затраты не считаются нулевыми.

## 5. Варианты и отдельные задачи

`variant_key` включает год и исходный код, например `ege_2013_trvar6`.
Дополнительные версии имеют собственную идентичность. Каждый вариант получает
свои источники, кэши, диагностические файлы, Excel, рисунки и архив.

`source_label` сохраняет исходную метку задачи, а `task_num` — её порядковый
номер внутри варианта. B1 и C1 различны. Фрагменты и `page_numbers` позволяют
собирать продолжения между страницами/колонками. Подпункты не становятся
самостоятельными строками Excel. Количество задач определяется источником.

Классификация использует полные деревья [exams.csv](../data/exams.csv) и
[topics.csv](../data/topics.csv). `exams_id` — один числовой лист ветки корня 2;
`topics_id` — один числовой лист ветки корня 1 либо новая тема строкой, если
подходящего листа нет. Номер старой задачи не определяет современную тему.
Структурная проверка ID и ограниченные семантические предупреждения не заменяют
проверку соответствия категории условию.

Созданы выдачи вариантов №1–12, содержащие 240 задач; это не набор отдельных
обработчиков «задач 1–12» и не подтверждение готовности этих выдач к импорту.
Общий CLI уже допускает номера 1–551: сам номер варианта 13 не требует нового
модуля. Потребность менять разбор,
рендер, OCR, классификацию или экспорт устанавливается по конкретному источнику
и воспроизводимому дефекту. Допустимый номер CLI сам по себе не подтверждает
совместимость конкретного источника с конвейером.

## 6. Хранение, кэши и возобновление

```text
input/catalogue/                         # локальный каталог реальных ссылок
input/cache/model_responses/             # общий кэш проверенных входов/ответов модели
harness/corrections/<variant_key>.json    # ручные категории/условия, не AI-кэш
input/variants/<variant_key>/source/      # источники и source_manifest.json
input/variants/<variant_key>/cache/
  ocr/page_001.json                       # проверенная страница
  conditions.json                        # сборка страниц
  classification.json
  fresh/<run_id>/                        # отдельный --fresh-ai
input/variants/<variant_key>/debug/
  content_review.json                    # содержательная сверка конкретных данных
  runs/<run_id>/                         # диагностика отдельной попытки
output/<variant_key>/                    # tasks.xlsx и рисунки
archives/<variant_key>_result.zip
reports/<run_id>/manifest.json
reports/<run_id>/<variant_key>.json
```

`source_manifest.json` связывает файлы с URL и SHA-256. Совпадение имени
недостаточно для принятия источника. Кэш OCR учитывает вариант/URL, хеш PDF,
страницу, рендер/DPI, настройки провайдера, версию/хеш промпта, версию схемы,
метки задач и хеши приложенных изображений ответов. Изменение PDF меняет identity
всех его страниц. При чтении страница проверяется снова.
`conditions.json` содержит собранные задачи, но не заменяет постраничный кэш.

`corrections.py` читает ручные `exams_id`/`topics_id` из отдельного JSON
версии 1–4; версия 2 дополнительно разрешает непустой `condition`,
версия 3 — заполнение пустого `answer` из опубликованного источника с URL
и методом `published-source-transcription`. Версия 4 разрешает исправление
непустого ответа по публикации с точным old и тем же provenance;
pipeline пересчитывает счётчики ответов после применения коррекций.
Identity включает вариант, URL и SHA-256 PDF; записи задают source_label,
поле, прежнее/новое значение, причину, evidence и метод проверки. Весь набор
валидируется до применения, исходные AI-кэши не меняются. Provenance попадает
в манифест и verification, а хеш файла — в fingerprint содержательной сверки.
Без файла механизм не меняет обычный поток. Пример —
[коррекции №13](../harness/corrections/ege_2013_trvar13.json).
Классификация исходного OCR читается до применения ручных условий,
поэтому их изменение не запускает новые модельные запросы. Категории
исправленного условия проверяются отдельно при содержательной сверке.

Кэш классификации дополнительно учитывает условия/метки, оба CSV, допустимые
категории и правила классификации. Изменение CSV не требует повторного OCR.
Тексты из `prompts/` загружаются без изменения пробелов/переносов. Неверный
или обрезанный ответ не становится готовым кэшем; уже проверенные страницы
сохраняются при сбое следующей страницы.

При промахе локального кэша этапы используют `content_cache.py`:
`input/cache/model_responses/<stage>/<fingerprint>.json`. Identity включает
хеш фактических сообщений и настройки совместимости. В OCR хешируются в том
числе base64 PNG страниц и ответов; учитываются рендер, схема и контекст меток.
Перенос в другой вариант допускается только при том же входе и повторной
валидации, локальный кэш получает identity текущего варианта.

Классификация v3 отправляет условия в стабильном порядке с номерами запроса,
без variant_key/source_label. После проверки номера сопоставляются текущим
задачам. Общий ключ учитывает весь пакет, оба CSV, допустимые категории,
промпт/схему/правила и настройки провайдера. Изображения сейчас передаются
только в OCR. Прежние локальные классификации v1/v2 проверяются с исходными
номерами при точной старой identity и не переписываются ради нового формата.
Исходный ответ и его SHA-256 сохраняются; неполный/повреждённый ответ не
используется. Явный cache_dir размещает этот кэш в собственном by_content,
изолируя --fresh-ai и его возобновление от общего кэша обычных запусков.

При успешном холодном потоке P страниц требуют P OCR + одну классификацию;
полный совместимый повтор — ноль модельных вызовов. Это норматив успешного
потока, дополнительные фактические попытки учитываются отдельно.

`--fresh-ai` создаёт отдельное дерево кэшей, `--resume` использует точные URL
и сохранённые пути кэшей внутри варианта. Совместное использование запрещено.
Старый Gemini OCR-кэш 542 принимается только для его точной идентичности,
совпадающего PDF и поддержанной полной legacy identity. Его происхождение
остаётся Gemini; старые Gemini-категории не становятся классификацией DeepSeek.

Содержательная сверка независима от AI-кэшей: её fingerprint включает PDF,
задачи, метаданные, хеши рисунков и восемь реальных модулей `exporting/` и
`formatting/`. Даже комментарий в таком модуле меняет fingerprint. Старые
findings сохраняются, но одобрение не переносится на несовместимые данные.
`resolved_warnings` одобренной сверки с совпадающим fingerprint может явно
устранить только существующие постраничные замечания, пришедшие из OCR,
с точным текстом, причиной и evidence. Исходные `ocr_warnings` и подтверждения
записываются в manifest/verification. Ошибки источников, классификации,
экспорта и missing_answers этим механизмом не устраняются.

## 7. Тестирование и локальные проверки

Основные тесты находятся в [tests/](../tests/). DeepSeek и Gemini подменяются
`FakeSession`, `FakeClient`, внедрёнными функциями и monkeypatch; HTTP-загрузки
тоже подменяются. Проверки записи используют временные каталоги. Часть тестов
читает реальные локальные артефакты 542 и пропускается при их отсутствии.
Общего запрета сети для всех тестов нет; текущие подмены не являются защитой
произвольного нового теста от сетевого обращения.

Тесты проверяют источники и метки, P+1/0 модельных вызовов, продолжения,
публикуемые ответы, совместимость кэшей, деревья категорий, ошибки API,
изоляцию вариантов, Excel/ZIP, откат публикации, рисунки и LaTeX/подпункты.
Соответствие областей кода тестам закреплено в §14 подробных инструкций.

Из корня проекта полная локальная регрессия в существующем окружении:

```bash
PYTHONDONTWRITEBYTECODE=1 DEEPSEEK_API_KEY='' GEMINI_API_KEY='' NVIDIA_API_KEY='' GROQ_API_KEY='' OPENROUTER_API_KEY='' .venv/bin/python -m pytest -q -p no:cacheprovider
```

Справка CLI без запуска обработки:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m alexlarin_parser --help
```

Для чистой документационной правки достаточно проверки ссылок, соответствия
коду и diff; полный набор тестов не требуется повторять:

```bash
git diff --check
git diff -- AGENTS.md .agents/agents.md docs/ARCHITECTURE.md
git status --short
```

Новые неотслеживаемые файлы нужно просматривать отдельно: обычный `git diff`
их не показывает.

`preview.html` принимает семь колонок TSV листа Tasks и две строки about.
Он не читает XLSX или файлы рисунков. MathJax требует сети; визуальная проверка
формул и отдельный просмотр рисунков дополняют автоматические тесты.

## 8. Ограничения и риски

- Корректные HTTP/JSON, существующие ID, целый ZIP и пройденные тесты
  не подтверждают математическую точность. У №1–12 остаются ошибки OCR и тем;
  актуальные findings и пути доказательств перечислены в §17 инструкций.
- Бесплатная цепочка проверена локально на подставном транспорте; доступность
  конкретных моделей/аккаунтов реальными API не проверена. Ограниченные
  эвристики классификации и векторных рисунков требуют содержательной/визуальной
  сверки. Ручные коррекции с происхождением поддерживают категории и условия;
  версия 3 также заполняет пустые ответы из проверенных публикаций с provenance.
  версия 4 исправляет также непустые ответы по публикациям с точным old.
- `--local-only` запрещает скачивания, но не модельные вызовы и не локальные
  записи. Повтор кэшей пересоздаёт сборку условий, выдачу и отчёты. Для проверки
  сохранности готовых артефактов нужен просмотр/сравнение, а не повтор конвейера.
- `--plan` не вызывает AI, но при выборе по каталогу без `--local-only` может
  скачать и сохранить каталог. Запуск без аргументов выбирает прежний №542.
- Корневые `check_deepseek.py` и `check_deepseek_ocr.py` содержат сетевой код
  на верхнем уровне: это не обычные тесты, их импорт тоже может вызвать сеть.
- Откат публикации относится к замене файлов. Сбой последующей записи
  verification/отчёта не гарантирует возврат уже опубликованной выдачи;
  статус и поля текущего/предыдущего результата нужно читать вместе.
- Коды CLI: 0 — SUCCESS или план, 2 — NEEDS_REVIEW, 1 — FAILED,
  130 — прерывание. NEEDS_REVIEW может сопровождаться Excel/ZIP, но не означает
  готовность к импорту.
- Исходники, кэши, результаты, отчёты и `.env` преимущественно исключены из Git.
  Новый клон не восстанавливает локальные доказательства и оплаченные результаты.
  Установленное окружение и `.env` не следует пересоздавать ради проверки карты.
