# Парсер тренировочных вариантов alexlarin.net

Проект собирает условия, опубликованные ответы и рисунки тренировочного варианта
по профильной математике. Условия распознаются через Gemini OCR.
Математические выражения в условиях и ответах сохраняются в LaTeX
для отображения через MathJax. Каждой задаче назначаются один тип задания
и одна учебная тема. Существующие категории выбираются из справочников;
если подходящей конечной темы нет, сохраняется название новой темы.

Проверенный источник: [тренировочный вариант № 542](https://alexlarin.net/ege/2026/trvar542.html).

## Результат

В папке `output/trvar542/` находятся пять файлов на одном уровне:

- `tasks.xlsx`;
- `image_82.jpeg` — рисунок задания 1;
- `image_83.jpeg` — рисунок задания 3;
- `image_198.png` — рисунок задания 8;
- `image_200.png` — рисунок задания 11.

В корне проекта создаётся `trvar542_result.zip` с этими же пятью файлами.
Имена и количество рисунков относятся к варианту № 542.

В Excel два листа. Лист `Tasks` содержит 19 заданий и семь колонок:

| Колонка | Содержание |
| --- | --- |
| `task_num` | Номер задания от 1 до 19 |
| `condition` | Условие с математическими выражениями в LaTeX |
| `image_name` | Имя файла рисунка; пусто, если рисунка нет |
| `solution` | Пусто: решения на этом этапе не требуются |
| `answer` | Опубликованный ответ строкой; математические выражения записаны в LaTeX |
| `exams_id` | Целый ID категории из `data/exams.csv` с непосредственным `parent_of_exam = 2` |
| `topics_id` | Целый ID конечной темы внутри математики из `data/topics.csv` либо текст новой темы |

На листе `about` первая строка содержит 11 названий полей по шаблону
получателя, вторая — значения:

| Поле | Содержание |
| --- | --- |
| `class` | Класс: 11 |
| `year` | Год экзамена: 2026 |
| `date` | В текущей реализации — дата формирования выгрузки |
| `topic` | Значение из справочника получателя |
| `exam_id` | Идентификатор экзамена по правилам получателя |
| `title` | Тренировочный вариант № 542 |
| `code` | Код варианта по правилам получателя |
| `source_name` | alexlarin.net |
| `is_public` | Признак публикации по правилам получателя |
| `source_url` | Ссылка на страницу варианта |
| `description` | Описание или инструкция к варианту |

`export_metadata.py` выбирает поля для Excel в этом порядке, переносит
название из внутреннего поля `variant_name` в `title` и определяет
`source_name` по домену ссылки. Исходный словарь метаданных сохраняется.
Служебные сведения об OCR и способе переноса ответов в лист `about`
не включаются.

Пока не заданы `topic`, `exam_id`, `code`, `is_public` и `description`,
их ячейки остаются пустыми. Поле `date` содержит дату формирования выгрузки;
дата публикации варианта не извлекается. Поле `about.exam_id` относится
ко всему варианту, а `Tasks.exams_id` — к типу отдельной задачи.

## Установка

Проект проверен на Python 3.12. Для недостающих исходников нужен доступ
к alexlarin.net, для нового распознавания или классификации — к Gemini API.
При готовых корректных исходниках и подходящих кэшах сборка работает без сети.

Из корня скачанного или клонированного проекта выполните:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Перед первым распознаванием или классификацией задайте ключ Gemini
в переменной окружения.
В Bash можно ввести его без отображения в терминале:

```bash
read -rsp "Ключ Gemini API: " GEMINI_API_KEY
printf '\n'
export GEMINI_API_KEY
```

## Запуск

Вариант по умолчанию:

```bash
python -u main.py
```

Явное указание ссылки:

```bash
python -u main.py --url "https://alexlarin.net/ege/2026/trvar542.html"
```

Распознавание уже скачанного PDF отдельной командой:

```bash
python -u recognizer.py --pdf input/trvar542.pdf
```

На этапе OCR при отсутствии подходящего кэша выполняются до 19 последовательных запросов
к Gemini: по одному на каждое задание. Результат сохраняется после каждого
успешного ответа. После сбоя повторный запуск продолжает обработку с недостающих
заданий при той же конфигурации.

Кэш OCR учитывает содержимое PDF, модель, инструкцию, разрешение изображений
и версию обработки. При совпадающем полном кэше повторных запросов OCR нет.
HTML, PDF, JavaScript и картинка ответов сначала проверяются в `input/`.
Подходящие файлы используются без повторного скачивания. Подробнее о проверках
и поведении при сбое — в разделе об исходниках ниже.

## Классификация задач

После получения условий `classification.py` подбирает для каждой задачи
ровно один `exams_id` и один `topics_id`. Все 19 условий и подготовленные
списки категорий передаются одним текстовым запросом. Формулы в условиях
передаются в LaTeX. Классификация использует распознанный текст.

Справочники находятся в `data/` и включаются в Git:

- `exams.csv`: разрешены только записи с **непосредственным**
  `parent_of_exam = 2` («математика профиль»). Наличие детей не мешает:
  179 «Вектор» и 8 «Планиметрия» допустимы, а их дочерние 180 и 178 — нет.
  Общего предка 2 недостаточно;
- `topics.csv`: разрешены только **листья внутри ветки «Математика»**
  с корнем 1. Лист — запись, у которой нет детей; её собственный `parent`
  обычно не равен нулю. Тема 526 допустима, родительская 98 и листья
  других предметов недопустимы.

Сначала проверяется структура всего CSV и строятся полные пути,
затем отбираются допустимые категории. Пропущенные родители, циклы,
повторяющиеся ID и пустые названия вызывают понятные ошибки.
Родители тем сохраняются в путях для контекста, но в варианты выбора не входят.

Модель видит полные пути категорий, например
`E | Вектор` и `T | Геометрия > Планиметрия > Векторы > Умножение вектора на число. Скалярное произведение векторов`.
Числовые ID скрыты от модели.
Префиксы `E` и `T` обозначают разные справочники. Для совпадающих полных
путей создаются разные подписи с суффиксами `[вариант 2]` и далее.

Ответ API — JSON-массив из 19 записей с полями:

- `task_num` — номер задания;
- `exam_choice` — точная подпись категории из списка `exams`;
- `topic_kind` — `existing` для существующей темы либо `new` для новой;
- `topic_choice` — точная подпись из `topics` либо короткое название новой темы.

Существующая подходящая конечная тема имеет приоритет. Если её нет, модель
придумывает название в том же общем запросе. Категория выбирается по полному
условию с учётом всех подпунктов, без таблицы соответствий номерам заданий.

Например, ответ модели для существующей темы:

```json
{
  "task_num": 2,
  "exam_choice": "E | Вектор",
  "topic_kind": "existing",
  "topic_choice": "T | Геометрия > Планиметрия > Векторы > Умножение вектора на число. Скалярное произведение векторов"
}
```

Python точно сопоставляет подписи с допустимыми категориями и получает:

```json
{"task_num": 2, "exams_id": 179, "topics_id": 526}
```

Пример новой темы (не специальное правило для номера 8):

```json
{
  "task_num": 8,
  "exam_choice": "E | Производная и первообразная",
  "topic_kind": "new",
  "topic_choice": "Первообразная и определённый интеграл"
}
```

Результат: `exams_id = 9`, `topics_id = "Первообразная и определённый интеграл"`.
Название сохраняется в той же седьмой колонке Excel как текст, включая защиту
от превращения строки в формулу. CSV автоматически не изменяются.

Новое название ограничено 120 символами и 16 словами. Пустые строки,
числа, формулы, HTML, служебные заглушки и копирование названия существующего
родителя отклоняются. Имя существующей темы другого предмета также не подходит.
Однозначное совпадение с названием допустимого листа после нормализации
регистра, пробелов, `ё` и пунктуации преобразуется в настоящий ID.
Неоднозначное совпадение вызывает ошибку, случайного выбора нет.
Смысловую уместность темы и отсутствие сюжетных деталей дополнительно
задаёт инструкция модели: проверка структуры не доказывает правильность
математической классификации.

Простая JSON-схема описывает четыре поля. Полноту всех номеров 1–19,
отсутствие повторов, типы значений и допустимость категорий Python проверяет
самостоятельно. `bool`, списки, неизвестные числовые ID и числовые строки
не принимаются. `exams_id` всегда остаётся целым числом.

При некорректном JSON, неизвестной подписи или неполном результате
выполняется один исправляющий запрос для всех задач. После второй неудачи
обработка прекращается. Всего классификация выполняет один или два запроса,
а при подходящем кэше — ни одного. Вторая попытка исправляет формат ответа
и выбор из списка; она не является отдельной проверкой математического смысла.

Тайм-аут запроса классификации — 120 секунд. Повторы HTTP в SDK отключены
через `HttpRetryOptions(attempts=1)`. Ошибка API или сети прерывает запуск
без автоматического второго запроса. При ошибке классификации прежняя папка
результата сохраняется: новая выгрузка готовится после успешной классификации.

Результат сохраняется в `input/trvar542_classification.json`. Кэш учитывает
условия, модель, уровень рассуждения, параметры запроса, инструкцию,
JSON-схему, версию правил и полную структуру обоих справочников: реальные ID,
названия и связи родителей. В нём сохраняются исходные подписи с `topic_kind`,
полученные числовые ID или строки новых тем и число использованных запросов.
Запись атомарная: новый JSON сначала записывается во временный файл,
затем заменяет прежний. Неудачный ответ старый кэш не перезаписывает.

Формат кэша обновлён до версии 2. Старый кэш с прежними правилами не подходит.
Даже при совпавшем ключе значения повторно проверяются по текущим правилам,
а исходный выбор декодируется и сверяется с сохранёнными значениями.
Повреждённый кэш также требует новой классификации. Изменения только
классификатора не затрагивают отдельный кэш OCR.

Для классификации без подходящего кэша нужен `GEMINI_API_KEY`, даже если
OCR-кэш уже готов. Настройки классификатора задаются константами `MODEL`
и `THINKING_LEVEL` в `classification.py`: сохранены `gemini-3.5-flash`,
уровень `medium` и тайм-аут 120 секунд. Новые правила не требуют изменения
этих настроек. OCR сохраняет отдельную модель `gemini-3.5-flash-lite`.

Лимит в один-два запроса относится к классификации всех 19 задач.
OCR — отдельный этап со своей моделью, настройками и кэшем. Счётчики разделены:
для OCR учитываются недостающие задания, для классификации — общие запросы
для всех 19 задач. Подходящий кэш соответствующего этапа означает ноль запросов
этого этапа. Проверок доступности и автоматического перебора моделей нет.

## Обработка данных

1. `downloader.py` через `load_source` использует проверенные локальные
   HTML, PDF, JavaScript и картинку ответов; скачивает только недостающие
   или непригодные исходники.
2. PyMuPDF читает текстовый слой для поиска номеров заданий, координат
   и метаданных. Регулярное выражение в `parsers.py` выделяет задания
   по обозначениям `1.`, `2.` и так далее.
3. `recognizer.py` готовит изображения областей заданий с разрешением 300 dpi.
   Gemini (`gemini-3.5-flash-lite`) распознаёт условия и возвращает JSON
   с формулами в LaTeX. Эти условия используются в итоговой таблице.
4. `latex_format.py` оформляет регулярными выражениями обозначения и числа
   в обычном тексте, исправляет пропуски пробелов вроде `равен10`
   и восстанавливает переносы перед подпунктами, записанные буквальными `\n`.
   Содержимое готовых формул в `$...$` и `$$...$$` сохраняется.
5. Ответы 1–12 извлекаются регулярным выражением из распакованного JavaScript.
6. Ответы 13–19 перенесены вручную с опубликованной
   [картинки ответов](https://alexlarin.net/ege/2026/trvar542.png)
   и хранятся в `input/trvar542_answers.json`. В этом же входном JSON
   сохранены ссылка на источник и способ переноса `manual_transcription`.
   Формулы в ответах 13, 15 и 18 записаны в LaTeX; дробь в ответе 17
   также оформлена через `\frac`. Эти сведения не добавляют служебных
   колонок в итоговый Excel.
7. Встроенные рисунки извлекаются через `page.get_images()` и связываются
   с заданиями по расположению в той же колонке. Для этого варианта служебные
   изображения находятся вне областей заданий и исключаются из результата.
8. `classification.py` назначает задаче по одному `exams_id` и `topics_id`,
   используя один общий запрос, при необходимости один исправляющий запрос
   и проверку по справочникам.
9. `task_html.py` добавляет `<br>` перед подпунктами А/Б/В в условиях
   и ответах. Формулы внутри `$...$` и `$$...$$` сохраняются; повторная
   обработка не добавляет лишние переносы. Задача с пунктами А и Б
   остаётся одной строкой Excel.
10. `export_metadata.py` подготавливает поля листа `about` по шаблону
    получателя. Результат передаётся в существующий экспорт:

    ```python
    write_excel(tasks, prepare_about_metadata(metadata), excel_path)
    ```

11. `exporter.py` записывает Excel и ZIP. Проверяются номера заданий,
    заполнение условий и ответов, наличие и состав файлов рисунков,
    а также целостность архива.

## Формулы и проверка через HTML

В ячейках Excel хранится текст LaTeX, например:

```text
Векторы $\vec{a}$ и $\vec{b}$. Длина вектора равна $\sqrt{43}$.
```

Ответы с математическими выражениями используют тот же формат, например:

```text
$[1;\log_2 3)\cup(3;\log_2 12]$
```

Простые числовые ответы могут оставаться обычным текстом, например
`Б) 125`. Десятичные ответы 1–12 сохраняются строками с исходными запятыми
и нулями, включая `0,9940`.

Для отображения формул используется вспомогательный файл `preview.html`,
подготовленный на основе HTML-примера задания. Он располагается в корне проекта.

1. Откройте `output/trvar542/tasks.xlsx` и выберите лист `Tasks`.
2. Скопируйте диапазон `A1:G20`, включая заголовки.
3. Откройте `preview.html` в браузере и вставьте строки в поле ввода.
4. Нажмите «Распарсить и отрисовать».

Страница показывает условия, ответы и имена файлов рисунков.
Теги `<br>` отображаются как переносы строк, другие HTML-теги
экранируются, чтобы сохранить текст и знаки сравнения в формулах. Для загрузки
MathJax нужен доступ в интернет. Ответ берётся из пятой колонки `answer`;
четвёртая колонка `solution` остаётся пустой. Колонки ID добавлены после
`answer` и не сдвигают ответ. Также поддерживается старый
формат из четырёх колонок, где ответ расположен четвёртым.

Например, условие с подпунктами хранится так:

```html
Общее условие.<br>А) Докажите утверждение.<br>Б) Найдите значение.
```

Сам Excel сохраняет LaTeX и `<br>` как текст. Математическое оформление выполняет
MathJax в браузере. Файл предпросмотра используется для проверки и хранится
отдельно от папки результата и итогового ZIP.

## Исходники и промежуточные файлы

В `input/` сохраняются скачанные исходники, текстовый слой PDF, кэш условий
`trvar542_conditions_gemini.json`, кэш классификации
`trvar542_classification.json` и ответы API. Изображения для OCR находятся
в `input/trvar542_ocr/`.

Для варианта 542 используются реальные сохранённые `trvar542.html`,
`trvar542.pdf`, `trvar542.js`, `trvar542.png`, `trvar542_answers.json`
и OCR-кэш. Локальное чтение PDF существовало ранее; тот же подход теперь
распространён на HTML, JS и PNG без отдельного сервиса или выдуманных данных.

`main.py` проверяет номер и год варианта в HTML/PDF, наличие ссылок на нужные
PDF/JS/PNG, нумерацию заданий PDF, все 12 ответов JavaScript и возможность
декодировать PNG. Сохранённый UTF-8 и исходный windows-1251 HTML поддерживаются.
Имена файлов и ссылки берутся для выбранного варианта; относительные ссылки
разрешаются через исходный URL alexlarin.net. `about.source_url` сохраняет
этот URL, а файл ответов 13–19 проверяется по ссылке на картинку источника.

Пустой или повреждённый файл не считается пригодным. Загруженные байты
проверяются **до** атомарной замены локального файла, поэтому страница ошибки
его не перезаписывает. Если подходящего локального исходника нет, а загрузка
недоступна, ошибка сообщает имя файла и URL. При всех готовых исходниках
и обоих подходящих кэшах обращения к alexlarin.net и Gemini не выполняются.

Перед новой выгрузкой прежняя папка результата переносится
в `input/previous_output/`. В `output/<variant_id>/` создаются Excel
и отдельные рисунки заданий. Служебные файлы остаются в `input/`.

В Git включаются код, тесты, документация, HTML для проверки, справочники
`data/*.csv` и JSON с вручную перенесёнными ответами. Скачанные исходники, OCR-кэш,
кэш классификации, резервные копии и итоговые файлы исключены через `.gitignore`.

## Тесты

```bash
python -m pytest -q
```

Тесты проверяют парсинг заданий и ответов, работу OCR-кэша, продолжение
обработки после сбоя, оформление LaTeX, переносы подпунктов, классификацию
всех задач одним запросом, ограничение до двух попыток, проверку ID,
прямого родителя exams, листья topics внутри математики, новые темы,
проверку и инвалидацию кэша, структуру листов Excel и состав ZIP.
В тестах OCR и классификации ответы API подменяются: ключ Gemini
и запросы к модели не нужны.

Интеграционные проверки копируют реальные исходники и OCR-кэш из `input/`
во временную папку, создают классификационный кэш тестовой подменой, затем
повторно собирают Excel/ZIP с полностью запрещённой сетью и Gemini.
Проверяется и сохранность прежней выгрузки при ошибке классификации.
Если локальные исходники не предоставлены вместе с клоном, эти проверки
пропускаются с объяснением причины. Тестовая классификация служит проверке
контракта и не является готовой математической классификацией варианта.

Структурные проверки не оценивают математический смысл распознанных формул
и точность выбора учебной темы. Существование ID в справочнике само по себе
не подтверждает, что тема подходит задаче.
После OCR условия нужно сверять с исходным PDF, а оформление — проверять
через MathJax.

## Границы применимости

Поиск областей рассчитан на две колонки, 19 заданий и номера в текстовом слое
PDF. Для сканов без текстового слоя или другой вёрстки потребуется доработка.

Регулярные выражения оформляют распознанную запись. Они не восстанавливают
формулы, неверно прочитанные OCR, и не заменяют проверку по источнику.
Непарный знак `$` или команда LaTeX вне формулы вызывает ошибку для проверки
границ выражения.

Для другого варианта нужно подготовить `input/<имя_pdf>_answers.json`
с ответами 13–19 и соответствующей ссылкой на опубликованную картинку,
затем проверить вёрстку, привязку рисунков и распознавание условий.
Один параметр `--url` не обеспечивает поддержку произвольного PDF.

Файл дополнительных ответов содержит поля `source_url`, `method` и `answers`.
Ключи ответов — строки от `"13"` до `"19"`; значения ответов также должны
быть строками. В JSON обратный слеш экранируется: например, команда LaTeX
`\frac` записывается как `\\frac`. После чтения JSON в ячейку Excel
попадает один обратный слеш.
